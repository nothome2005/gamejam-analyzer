## 1. Вступ (Introduction)

### 1.1. Призначення документа
Цей документ описує формальні вимоги до інформаційної системи **Game Jam Analyzer**. Документ розроблено відповідно до рекомендацій стандарту IEEE 830 та сучасної методології специфікування через приклади (Specification by Example). Документ є нормативним еталоном для проєктування архітектури, розробки компонентів, створення автоматизованих тестів та оцінки відповідності реалізації в наступних циклах розробки (SDD — Specification-Driven Development).

### 1.2. Межі системи (Scope)
#### 1.2.1. Входить до системи (In-Scope, v1.0):
1. **Облік та конфігурація джемів**: створення подій, встановлення регламенту, тем, часових рамок початку, дедлайну та періоду суддівства.
2. **Управління учасниками та командами**: реєстрація користувачів, облік спеціалізацій (Gameplay Programmer, 2D/3D Artist, Sound Designer тощо), об'єднання у команди.
3. **Реєстрація та аудит робіт (Submissions)**:
   - Внесення посилань на репозиторії сирцевого коду Git (GitHub, GitLab тощо).
   - Фіксація та перевірка формату хеш-суми релізу за алгоритмом SHA-256 для гарантування незмінності коду після дедлайну.
   - Декларація сторонніх асетів (Asset Inventory: графіка, музика, готові бібліотеки) для оцінки оригінальності.
   - Фіксація зовнішніх посилань дистрибуції білдів (Itch.io, GameJolt, WebGL).
   - Валідація ліміту розміру дистрибутиву (до 500 МБ).
4. **Політика дедлайнів (Soft Deadline Handling)**: облік точного часу подання, автоматичне маркування робіт, надісланих після дедлайну (`is_late: true`), фіксація затримки та нарахування штрафних балів.
5. **Життєвий цикл статусів та закрите суддівство**:
   - Статуси: `Draft` $\rightarrow$ `Submitted` $\rightarrow$ `Under Review` $\rightarrow$ `Completed`.
   - Захист відкритості: під час етапу `Under Review` доступ до робіт та оцінок мають лише оргкомітет і журі.
6. **Суддівська колегія та оцінювання**: оцінювання за 5 критеріями (Gameplay, Theme, Graphics, Audio, Code Quality) за 5-бальною шкалою (1–5) із розрахунком зваженого рейтингу.
7. **Аналітика та підсумкові звіти**:
   - Автоматичний розрахунок і публікація лідерборду.
   - Статистичний аналіз популярності ігрових рушіїв (Unity, Unreal Engine, Godot, Custom Frameworks) та жанрів.

#### 1.2.2. Не входить до системи (Out-of-Scope, v1.0):
1. **Власний важкий файловий хостинг**: зберігання фізичних білдів розміром понад 500 МБ на власних серверах системи не передбачено (використовуються зовнішні посилання Itch.io/GameJolt).
2. **Вбудований хмарний WebGL-раннер**: система не емулює запуск важких 3D-ігор безпосередньо у своєму бекенді.
3. **Платіжні шлюзи та грошові винагороди**: система не здійснює монетарні транзакції між організаторами та переможцями.
4. **Синхронний чат реального часу**: комунікація команд під час розробки ведеться на зовнішніх платформах (Discord, Telegram).

## 3. Загальний опис системи (Overall Description)

### 3.1. Рольова модель користувачів (Actors)
1. **Гість / Спільнота (Guest / Player)**: неавторизований відвідувач. Може переглядати відкриті джеми, ігри завершених джемів, читати опис та переходити за посиланнями на зовнішні WebGL-білди.
2. **Учасник (Participant)**: зареєстрований користувач. Може створювати команду, приєднуватися до команди, заповнювати свій профіль спеціалізації.
3. **Капітан команди (Team Captain)**: учасник, який створив команду. Володіє правами оформлення та відправки картки проєкту (Submission), внесення ревізій та декларації асетів.
4. **Член журі (Judge)**: користувач із суддівським доступом. Має доступ до сабмішнів на етапі `Under Review`, оцінює проєкти за 5 критеріями, пише закриті або відкриті коментарі.
5. **Організатор джему (Organizer)**: створює регламент джему, налаштовує критерії, керує списком суддів, переводить статуси джему, затверджує лідерборд.

### 3.2. Операційне середовище та обмеження
- Архітектурний патерн: Клієнт-серверна веб-система з RESTful API.
- Персистентність: Реляційна база даних (PostgreSQL / SQLite для тестування) з ACID-транзакціями для реєстрації оцінок та сабмішнів.
- Обмеження часу: робота із часовими поясами здійснюється у форматі UTC (ISO 8601).

## 4. Функціональні вимоги (Functional Requirements)

### REQ-F-001: Створення та конфігурація ігрового джему
- **Опис**: Організатор повинен мати можливість створити новий джем, задати назву, опис, тему, дату початку (`start_time`), дедлайн подання робіт (`submission_deadline`), завершення суддівства (`review_deadline`) та регламент штрафів за запізнення.
- **Критерій прийняття AC-F-001**: Джем успішно зберігається в базі даних зі статусом `Created` або `Active`; валідація перевіряє, що `start_time < submission_deadline < review_deadline`.

### REQ-F-002: Реєстрація команд та управління складом
- **Опис**: Учасники джему повинні мати можливість створювати команду, генерувати інвайт-код для партнерів та призначати ролі (Gameplay Programmer, 2D/3D Artist, Sound Designer).
- **Критерій прийняття AC-F-002**: Кожен учасник може належати щонайбільше до однієї команди в межах одного джему; капітан має право виключати учасників до настання дедлайну.

### REQ-F-003: Подання проєкту (Submission) з аудиторськими даними
- **Опис**: Капітан команди повинен надати дані про гру: назву, опис, ігровий рушій (вибір зі списку або введення Custom), прямий URL на публічний репозиторій сирцевого коду Git, commit hash релізу, хеш-суму SHA-256 та перелік сторонніх асетів (Asset Inventory).
- **Критерій прийняття AC-F-003**: Система не дозволяє збереження сабмішну, якщо Git URL не валідний або поле SHA-256 не відповідає формату 64 шістнадцяткових символів `^[a-fA-F0-9]{64}$`.

### REQ-F-004: Фіксація параметрів дистрибуції та перевірка ваги білда
- **Опис**: Капітан повинен вказати URL на зовнішню дистрибуцію білда (Itch.io, GameJolt, GitHub Pages) та задекларований розмір дистрибутиву (в мегабайтах).
- **Критерій прийняття AC-F-004**: Якщо вказаний розмір перевищує 500 МБ, система видає попередження про порушення регламенту з вимогою оптимізації білда.

### REQ-F-005: Облік часових рамок та підтримка м'якого дедлайну (Soft Deadline)
- **Опис**: Система повинна фіксувати точний серверний час (UTC) кожного збереження сабмішну. Якщо відправка відбулася після `submission_deadline`, системі заборонено повністю відхиляти запит; замість цього сабмішн позначається прапорцем `is_late: true`, фіксується затримка в хвилинах та розраховується штрафний бал.
- **Критерій прийняття AC-F-005**: Для всіх сабмішнів, надісланих у проміжку між `submission_deadline` та `review_deadline`, атрибут `is_late` встановлюється в `true`, а штраф становить фіксований відсоток (наприклад, -5% за кожну годину затримки) відповідно до налаштувань джему.

### REQ-F-006: Регламент життєвого циклу статусів та захист етапу оцінювання
- **Опис**: Сабмішн проходить життєвий цикл статусів: `Draft` $\rightarrow$ `Submitted` $\rightarrow$ `Under Review` $\rightarrow$ `Completed`.
- **Критерій прийняття AC-F-006**: На етапі `Under Review` звичайні відвідувачі та учасники-суперники не мають доступу до сирцевих кодів, оцінок та рецензій журі; спроба неавторизованого читання повертає помилку HTTP 403 Forbidden.

### REQ-F-007: Мультикритеріальне оцінювання журі
- **Опис**: Призначений член журі повинен мати доступ до інтерфейсу оцінювання закріплених робіт за 5 критеріями: Gameplay, Theme Relevance, Graphics, Audio, Code Quality за шкалою від 1 до 5 цілих балів та опціонального текстового коментаря.
- **Критерій прийняття AC-F-007**: Оцінка фіксується в системі із прив'язкою до ідентифікатора судді; спроба виставити оцінку поза діапазоном 1–5 повертає помилку валідації. Суддя не може оцінювати проєкт власної команди.

### REQ-F-008: Автоматичний розрахунок рейтингу та генерація лідерборду
- **Опис**: Після завершення періоду суддівства організатор переводить джем у статус `Completed`, після чого система автоматично обчислює середні оцінки за кожною категорією, сумарний бал, віднімає штрафні бали за `is_late` та будує ранжований список команд.
- **Критерій прийняття AC-F-008**: Лідерборд формується детерміновано; у разі рівності підсумкових балів перевага надається проєкту з вищим балом за Gameplay, потім — за Theme Relevance.

### REQ-F-009: Аналітичний облік та звітність щодо ігрових рушіїв
- **Опис**: Система повинна агрегувати дані про використані інструменти розробки в межах окремого джему та глобально по системі (Unity, Unreal Engine, Godot, GameMaker, Custom) з побудовою процентного розподілу.
- **Критерій прийняття AC-F-009**: Запит аналітики повертає JSON-звіт із кількістю проєктів та часткою кожного рушія, відсортований за спаданням популярності.

### REQ-F-010: Публічний каталог проєктів джему
- **Опис**: Для завершених джемів система формує публічну сторінку-галерею з переліком ігор, скріншотами, посиланнями на зовнішній WebGL-запуск та інформацією про команду.
- **Критерій прийняття AC-F-010**: Будь-який неавторизований користувач може отримати список проєктів з пагінацією та фільтрацією за жанрами, рушієм і призовим місцем.

## 5. Нефункціональні вимоги (Non-Functional Requirements)

### REQ-NF-001: Продуктивність формування лідерборду та аналітики
- **Опис**: Час відгуку системи при розрахунку та відображенні лідерборду для джему з кількістю до 500 сабмішнів не повинен перевищувати 1.5 секунди при 95-му перцентилі (p95).
- **Критерій прийняття AC-NF-001**: Навантажувальний тест на агрегацію результатів 500 проєктів завершується за час $t \le 1.5$ с.

### REQ-NF-002: Безпека та ізоляція суддівських даних
- **Опис**: Оцінки журі та коментарі до офіційного оголошення результатів повинні зберігатися з розмежуванням доступу на рівні бекенду (Role-Based Access Control).
- **Критерій прийняття AC-NF-002**: Жоден API-ендпоінт для ролей `Participant` або `Guest` не повинен повертати об'єкти оцінок до зміни статусу джему на `Completed`.

### REQ-NF-003: Цілісність аудиторського сліду (Auditability & Immutability)
- **Опис**: Будь-які зміни в полях `git_url`, `commit_hash`, `sha256_checksum` після первинної відправки повинні логуватися в системному аудит-журналі із фіксацією автора, мітки часу та попереднього значення.
- **Критерій прийняття AC-NF-003**: При зміні реквізитів у таблиці аудит-логу з'являється незмінний запис; модифікація або видалення записів аудит-логу заборонені.

### REQ-NF-004: Надійність та стійкість до збоїв
- **Опис**: Форма подання проєкту повинна підтримувати автозбереження чернетки (Draft) у локальному сховищі браузера або на сервері для запобігання втраті даних через обрив інтернет-з'єднання.
- **Критерій прийняття AC-NF-004**: У разі симуляції скидання з'єднання після відновлення сторінки відновлюються всі введені текстові поля форми.

### REQ-NF-005: Зручність використання (Usability)
- **Опис**: Інтерфейс подання робіт та оцінювання повинен бути адаптивним для екранів з роздільною здатністю від 375px до 4K та відповідати контрастності WCAG 2.1 AA.
- **Критерій прийняття AC-NF-005**: Валідація інтерфейсу інструментами Lighthouse показує рівень доступності Accessibility $\ge 90$ балів.

### REQ-NF-006: Супровідність та масштабованість (Maintainability)
- **Опис**: Архітектура валідаторів цілісності коду та взаємодії із зовнішніми Git-сервісами повинна бути реалізована за патерном Адаптер (Adapter/Strategy) для ізоляції сторонніх API.
- **Критерій прийняття AC-NF-006**: Додавання нового провайдера (наприклад, Bitbucket) не потребує зміни базової бізнес-логіки обробки сабмішнів.

## 6. Вимоги до зовнішніх інтерфейсів

1. **Інтерфейс користувача (GUI)**:
   - Сторінка джему (таймер зворотного відліку до дедлайну, регламент, список учасників).
   - Форма сабмішну із секціями: Загальна інформація, Аудит коду (Git/SHA-256), Дистрибуція (WebGL/External URL), Перелік асетів.
   - Кабінет члена журі зі зручною карткою оцінювання (зірковий або слайдерний рейтинг 1–5).
2. **Програмні інтерфейси (REST API)**:
   - `POST /api/v1/jams/{jam_id}/submissions` — подання або оновлення проєкту.
   - `POST /api/v1/submissions/{submission_id}/verify-hash` — запуск перевірки SHA-256 хешу.
   - `POST /api/v1/submissions/{submission_id}/evaluations` — фіксація суддівського оцінювання.
   - `GET /api/v1/jams/{jam_id}/leaderboard` — отримання підсумкової таблиці.
   - `GET /api/v1/analytics/engines` — статистика використання ігрових рушіїв.

## 7. Сценарії BDD (Specification by Example, Given–When–Then)

### BDD-SC-001: Успішне подання проєкту до настання дедлайну
```gherkin
Feature: Подання проєкту на ігровий джем

  Scenario: Вчасне подання гри з коректними контрольними даними
    Given джем "Winter Indie Jam 2026" перебуває у статусі "Active"
    And поточний час 2026-10-02 18:00 UTC менший за дедлайн джему 2026-10-02 20:00 UTC
    And капітан команди "PixelCrafters" заповнив форму проєкту:
      | Field            | Value                                                          |
      | title            | Frostbite Odyssey                                              |
      | engine           | Godot 4.3                                                      |
      | git_url          | https://github.com/pixelcrafters/frostbite-game.git            |
      | commit_hash      | e4d909c290d0fb1ca068ffaddf22cbd0a6042db5                      |
      | sha256_checksum  | e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855 |
      | build_url        | https://pixelcrafters.itch.io/frostbite-odyssey                |
      | build_size_mb    | 120                                                            |
    When капітан надсилає проєкт на реєстрацію
    Then система зберігає сабмішн зі статусом "Submitted"
    And прапорець "is_late" встановлюється у "false"
    And штрафні бали "penalty_points" дорівнюють 0
```

### BDD-SC-002: М'який дедлайн: подання проєкту після завершення основного часу
```gherkin
Feature: Обробка м'якого дедлайну

  Scenario: Подання проєкту із запізненням на 45 хвилин
    Given джем "Winter Indie Jam 2026" має дедлайн прийому робіт 2026-10-02 20:00 UTC
    And поточний серверний час становить 2026-10-02 20:45 UTC
    And період суддівства ще не розпочався (дедлайн закриття прийому 2026-10-02 23:00 UTC)
    When капітан команди "RetroSquad" надсилає проєкт "Neon Dash"
    Then система успішно приймає проєкт зі статусом "Submitted"
    And прапорець "is_late" встановлюється у "true"
    And система фіксує тривалість запізнення "late_minutes = 45"
    And команді нараховується штраф "late_penalty" згідно з регламентом
    And капітан бачить попередження "Роботу прийнято із запізненням. Нараховано штрафні бали"
```

### BDD-SC-003: Відхилення некоректного формату контрольної суми SHA-256
```gherkin
Feature: Валідація цілісності та аудиту коду

  Scenario: Спроба надіслати некоректний хеш SHA-256
    Given капітан команди заповнює форму реєстрації проєкту
    When у полі "sha256_checksum" введено значення "invalid-hash-string-too-short"
    And натиснуто кнопку "Зберегти проєкт"
    Then система відхиляє збереження
    And повертає помилку валідації "Контрольна сума повинна містити рівно 64 шістнадцяткові символи"
    And статус сабмішну залишається "Draft"
```

### BDD-SC-004: Захист конфіденційності робіт на етапі закритого суддівства
```gherkin
Feature: Розмежування доступу до робіт

  Scenario: Спроба стороннього відвідувача переглянути деталі коду під час суддівства
    Given джем перебуває у статусі "Under Review"
    And проєкт "Shadow Run" має статус "Submitted"
    When неавторизований користувач або учасник іншої команди запитує "GET /api/v1/submissions/42"
    Then сервер повертає статус відповіді 403 Forbidden
    And деталі сирцевого коду, суддівські бали та коментарі не передаються у відповіді
```

### BDD-SC-005: Мультикритеріальне оцінювання та перерахунок рейтингу
```gherkin
Feature: Оцінювання проєктів журі

  Scenario: Член журі виставляє валідні бали за всіма 5 критеріями
    Given авторизований член журі з ID "judge-07"
    And джем перебуває на етапі "Under Review"
    When суддя виставляє для проєкту "Frostbite Odyssey" оцінки:
      | Criterion        | Score |
      | Gameplay         | 5     |
      | Theme Relevance  | 4     |
      | Graphics         | 4     |
      | Audio            | 5     |
      | Code Quality     | 5     |
    And надсилає рецензію з коментарем "Відмінна оптимізація шейдерів у Godot"
    Then система зберігає оцінку в базі даних
    And підсумковий зважений бал проєкту автоматично перераховується
    And формується запис у журналі суддівської активності
```

### BDD-SC-006: Валідація перевищення максимального розміру дистрибутиву
```gherkin
Feature: Валідація дистрибутиву

  Scenario: Спроба зареєструвати білд розміром понад 500 МБ
    Given капітан команди вказує метадані білда
    When у полі "build_size_mb" зазначено значення 750
    Then система відображає блокуюче попередження "Розмір білда перевищує допустимий ліміт джему (500 МБ)"
    And вимагає підтвердження оптимізації або дозволу оргкомітету
```
