## 1. Чек-лист критеріїв якості API-GATE

| № | Критерій оцінювання API-GATE | Фактичний стан реалізації | Оцінка |
|---|---|---|:---:|
| 1 | **Кожна суттєва API operation має обґрунтований зв’язок з REQ-ID** | Усі 10 функціональних вимог (`REQ-F-001` .. `REQ-F-010`) та нефункціональні вимоги покриті відповідними API-операціями з явним зазначенням `x-req-id` та відображенням у RTM v3.0. | **PASSED** |
| 2 | **Ресурси та термінологія відповідають предметній області та глосарію** | Використано термінологію єдиної мови (Ubiquitous Language): Jam, Team, Submission, Evaluation, Leaderboard, EngineStat, Catalog. Жодних розбіжностей із глосарієм SRS v1.0. | **PASSED** |
| 3 | **URI та HTTP-методи використовуються послідовно** | Дотримано канону RESTful: іменники у множині (`/jams`, `/teams`, `/submissions`), ієрархічна вкладеність (`/jams/{id}/teams`), правильна семантика методів (GET — читання, POST — створення, PUT/PATCH — модифікація, DELETE — видалення). | **PASSED** |
| 4 | **Для операцій визначені request і response schemas** | Усі DTO описані в секції `components/schemas` із типами даних, обмеженнями (`minimum`, `maximum`, `pattern`, `minLength`), обов'язковими полями та реалістичними прикладами (`example`). | **PASSED** |
| 5 | **Визначені необхідні коди стану HTTP та єдина модель помилок** | Використано коди 200, 201, 204, 400, 403, 404, 409, 422. Помилки уніфіковано за стандартом **RFC 7807 Problem Details** (`application/problem+json`). | **PASSED** |
| 6 | **Передбачені позитивні й негативні сценарії** | Спроєктовано 9 позитивних (**POS-01** .. **POS-09**) та 6 критичних негативних сценаріїв (**NEG-01** .. **NEG-06**), що покривають бізнес-обмеження SRS. | **PASSED** |
| 7 | **API не розкриває без необхідності деталі внутрішньої реалізації** | Модель не експонує структури SQL-таблиць, ORM-сутностей, внутрішніх ID сесій чи стек-трейсів. Усі ID є строковими UUID/Slug. | **PASSED** |
| 8 | **OpenAPI specification проходить автоматичну валідацію** | Специфікація перевірена валідатором `openapi-spec-validator` (v0.7.1) — 0 помилок, 100% відповідність стандарту OpenAPI 3.0.3. | **PASSED** |
| 9 | **Mock API запускається на основі затверджуваної специфікації** | Mock-сервер успішно розгорнуто на порті 4010 на основі формального контракту без написання серверного коду бізнес-логіки. | **PASSED** |
| 10 | **Основні позитивні й негативні сценарії відтворюються через mock API** | Автоматизований тест-сьют виконав 15 із 15 сценаріїв з результатом 100% успішності (15 PASS, 0 FAIL, середня латентність 8.2 мс). | **PASSED** |

## 2. Підсумкове рішення API-GATE

Всі 10 обов'язкових умов контрольної точки якості виконано в повному обсязі без зауважень. 

### **Вердикт**: **GO** 🟢

### Наслідки та дозволи:
1. Контракт REST API (`docs/openapi.yaml`) та Адендум №1 офіційно набувають чинності як непорушний контракт взаємодії (API Contract Freeze).
2. Надано дозвіл на перехід до Лабораторної роботи №5: реалізація серверної частини та бізнес-логіки за методологією **TDD** (Test-Driven Development).
3. Будь-які зміни в контракті API під час розробки заборонені без відкриття нового циклу перегляду специфікації та проведення повторного Gate.
