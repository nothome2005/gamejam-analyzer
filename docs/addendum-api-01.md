### 1. Передумови та мета адендуму
Під час переходу від затверджених вимог SRS v1.0 до формального контракту OpenAPI 3.0.3 за методологією **API-First** виникла необхідність деталізувати та формалізувати низку технічних аспектів поведінки системи, які в базовій специфікації були описані на рівні бізнес-правил без деталізації протоколу передачі даних.

Згідно з каноном SDD (Specification-Driven Development), будь-яка нова або уточнена поведінка API **не може непомітно додаватися до коду чи специфікації**; вона повинна проходити формальне узгодження через офіційний Адендум із фіксацією обґрунтування та впливу на предметну область.

### 2. Реєстр уточненої та нової поведінки API

#### 2.1. Уточнення ADD-01: Стандартизація єдиної моделі помилок (RFC 7807 Problem Details)
- **Початковий стан в SRS v1.0**: Зазначалися лише орієнтовні HTTP-коди (403 Forbidden, 422 Unprocessable Entity) без фіксації структури JSON-тіла помилки.
- **Уточнена специфікація**: Для всіх клієнтських та серверних помилок (коди 400, 401, 403, 404, 409, 422, 500) запроваджено єдиний галузевий стандарт **RFC 7807 (Problem Details for HTTP APIs)** із медіа-типом `application/problem+json`.
- **Схема структури**:
  ```json
  {
    "type": "https://gamejam-analyzer.local/errors/unprocessable-entity",
    "title": "Unprocessable Entity",
    "status": 422,
    "detail": "Поле 'sha256_checksum' повинно містити рівно 64 шістнадцяткові символи.",
    "instance": "/api/v1/jams/jam-winter-2026/submissions",
    "invalid_params": [
      {
        "name": "sha256_checksum",
        "reason": "Значення не відповідає регулярному виразу ^[a-fA-F0-9]{64}$"
      }
    ]
  }
  ```
- **Обґрунтування**: Забезпечує машинно-зчитувану діагностику помилок, усуває неоднозначність парсингу на фронтенді та мобільних клієнтах, спрощує локалізацію інцидентів у логах.

---

#### 2.2. Уточнення ADD-02: Декомпозиція ендпоінтів команд та управління інвайт-кодами (REQ-F-002)
- **Початковий стан в SRS v1.0**: Описано вимогу створення команди та призначення ролей учасників без фіксації REST-маршрутів.
- **Уточнена специфікація**:
  - `POST /api/v1/jams/{jam_id}/teams` — реєстрація команди, призначення автора капітаном та автоматична генерація унікального інвайт-коду (формат `PXL-XXXX`).
  - `GET /api/v1/jams/{jam_id}/teams` — отримання списку команд джему.
  - `GET /api/v1/teams/{team_id}` — отримання картки команди та списку учасників із ролями.
  - `POST /api/v1/teams/{team_id}/members` — приєднання до команди за інвайт-кодом із передачею фіксованого enum спеціалізації:
    - `Gameplay Programmer`
    - `2D/3D Artist`
    - `Sound Designer`
    - `Level Designer`
    - `Game Designer`
    - `Narrative Designer / Writer`
  - `DELETE /api/v1/teams/{team_id}/members/{user_id}` — виключення учасника капітаном команди (повертає 204 No Content). При спробі виконати дію не капітаном повертається 403 Forbidden.
- **Обґрунтування**: Повна RESTful ізоляція ресурсу `Team` та підресурсу `Members`, що запобігає маніпуляціям зі складом команд сторонніми особами.

---

#### 2.3. Уточнення ADD-03: Формалізація переходу статусів джему (`PATCH /jams/{jam_id}/status`)
- **Початковий стан в SRS v1.0**: Зазначено, що організатор переводить статуси джему (`Created` $\rightarrow$ `Active` $\rightarrow$ `Under Review` $\rightarrow$ `Completed`).
- **Уточнена специфікація**: Введено спеціалізований ендпоінт `PATCH /api/v1/jams/{jam_id}/status`. Запит приймає схему `JamStatusUpdate` зі строгим enum переліком статусів. При порушенні хронологічного ланцюжка (наприклад, спроба перевести `Created` відразу в `Completed`) сервер повертає 422 Unprocessable Entity з описом порушеного інваріанту.
- **Обґрунтування**: Гарантує цілісність автоматного стану (Finite State Machine) джему та блокує несанкціоноване відкриття або закриття голосування.

---

#### 2.4. Уточнення ADD-04: Стандартизація пагінації та фільтрації (REQ-F-010, REQ-NF-001)
- **Початковий стан в SRS v1.0**: Згадано фільтрацію за рушіями та пагінацію в каталозі.
- **Уточнена специфікація**: Для колекцій (`/jams`, `/catalog/jams`, `/catalog/projects`) стандартизовано query-параметри `limit` (ціле, за замовчуванням 20, максимум 100) та `offset` (ціле, за замовчуванням 0). Для каталогу проєктів додано параметри `engine` та `jam_id`.
- **Обґрунтування**: Захищає сервер від вичерпання оперативної пам'яті (Memory Exhaustion DoS) при великій кількості робіт і гарантує виконання вимоги продуктивності REQ-NF-001 ($t \le 1.5$ с).

---

#### 2.5. Уточнення ADD-05: Ендпоінт діагностики стану сервісу (`GET /health`)
- **Початковий стан в SRS v1.0**: Відсутній.
- **Уточнена специфікація**: Додано легкозважний неавторизований ендпоінт `GET /api/v1/health`, що повертає JSON із полями `status: "healthy"`, `version: "1.0.0"` та поточним точним серверним часом у форматі UTC `server_time_utc` (ISO 8601).
- **Обґрунтування**: Необхідний для Kubernetes/Docker healthcheck probes, а також для синхронізації локального таймера клієнта із серверним часом дедлайну джему для запобігання випадковим штрафам за Soft Deadline.

---

#### 2.6. Уточнення ADD-06: Специфікація авторизаційних схем для тестування (Security Schemes)
- **Початковий стан в SRS v1.0**: Вказано вимогу RBAC захисту.
- **Уточнена специфікація**: У OpenAPI визначено дві схеми безпеки:
  1. `BearerAuth` (HTTP Bearer JWT) — продуктовий стандарт авторизації.
  2. `RoleAuth` (`X-User-Role` header: `Guest`, `Participant`, `Judge`, `Organizer`) — для детермінованого тестування mock API та швидкої емуляції прав доступу на етапі прототипування.
- **Обґрунтування**: Дозволяє відтворювати негативні сценарії RBAC (HTTP 403) безпосередньо через mock-сервер без необхідності розгортання повноцінного OAuth2/OIDC провайдера.

### 3. Висновок щодо впливу на систему
Запропоновані уточнення повністю узгоджуються з архітектурними рамками системи, не порушують виділених у SRS меж (Scope), усувають неоднозначності реалізації та забезпечують 100% готовність контракту до початку розробки за TDD у наступній лабораторній роботі.
