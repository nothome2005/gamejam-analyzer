- **Відповідальні**: Маслов Андрій (Lead Engineer / Product Owner), Antigravity AI Agent (Coding Agent)

## 1. Вибір системи багтрекінгу

Для реалізації проєкту обрано **GitHub Projects & GitHub Issues**, інтегровані безпосередньо у репозиторій `nothome2005/gamejam-analyzer`.

### Обґрунтування вибору:
1. **Нативна інтеграція з Git**: пряма прив'язка комітів (`Fixes #12`, `Refs #15`), автоматичне переміщення карток при відкритті та злитті Pull Request.
2. **Підтримка міток (Labels)**: гнучке маркування типів тікетів (`type:spec`, `type:test`, `type:feature`, `type:gate` тощо), ролей (`assignee:agent`, `assignee:human`) та вимог (`req:REQ-F-003`).
3. **Підтримка Milestones (Контрольних точок)**: прив'язка задач до етапів та stage-gates (`PLAN-GATE`, `GATE-AUDIT`, `RELEASE-GATE`).
4. **Прозорість історії змін та аудиту**: незмінний журнал дій над кожною задачею відповідно до вимог SDD.

## 2. Базовий робочий процес (Workflow Statuses)

Робочий процес відображає рух задач через стани з урахуванням специфіки SDD та ролі контрольних точок:

| Статус | Опис стану | Можливі наступні стани | Хто відповідальний за перехід |
|---|---|---|---|
| **Backlog** | Задача зареєстрована, сформульована на основі SRS, але ще не запланована в активний спринт. | `Ready (To Do)` | Product Owner (Людина) |
| **Ready (To Do)** | Задача повністю специфікована, залежності розблоковано, критерії прийняття зафіксовано. | `In Progress`, `Blocked` | Студент / Кодинговий агент |
| **In Progress** | Активна робота над кодом, тестом чи документом. Для задач типу `Feature` розробка дозволена лише за наявності готового `Test`. | `Verification`, `Blocked` | Виконавець (Агент або Людина) |
| **Verification** | Автоматизована перевірка: проходження тест-сьюту (pytest/behave), перевірка лінтером, статичний аналіз коду. | `In Review (Validation)`, `In Progress` (у разі фейлу) | Автоматизований CI / Кодинговий агент |
| **Validation / In Review** | Перевірка людиною: код-рев'ю, валідація відповідності бізнес-вимозі та критерію прийняття (AC). | `Gate`, `Done`, `Blocked` | Людина (Студент) |
| **Gate (Pending Decision)** | Контрольна точка якості етапу (Stage-Gate). Блокує старт наступної фази реалізації. | `Done (GO)`, `Revise (REVISE)` | Тільки Людина (Human-Only) |
| **Blocked / Revise** | Виконання призупинено через виявлену блокуючу проблему, прогалину у специфікації або відхилення на Gate. | `Ready`, `Backlog` | Людина (з оформленням Addendum) |
| **Done** | Критерії прийняття повністю виконано, тести зелені, зміни злито в основну гілку. | *(Кінцевий стан)* | Людина |

## 3. Типи тікетів відповідно до SDD-циклу

| Тип тікета | Префікс мітки | Призначення та опис | Правило блокування / залежності |
|---|---|---|---|
| **Specification** | `type:spec` | Формалізація або деталізація вимог SRS, структури схем та API. | Передує всім іншим типам задач. |
| **Addendum** | `type:addendum` | Офіційне версіоване доповнення або зміна до вже затвердженої специфікації SRS v1.0. | Блокує реалізацію нових фіч до затвердження людиною. |
| **Test** | `type:test` | Розробка тест-кейсів, BDD-сценаріїв (`behave`/`pytest-bdd`), unit-тестів до написання коду (TDD/ATDD). | **Блокує** початок задачі `Feature`. |
| **Feature** | `type:feature` | Реалізація виробничого коду системи строго в межах вимог SRS. | Заблокована до завершення відповідного `Test`. |
| **Verification** | `type:verification`| Автоматизований запуск тестів, перевірка лінтерами та метриками якості. | Виконується після завершення `Feature`. |
| **Validation** | `type:validation`  | Людська оцінка зручності (UX/UI), відповідності первинному задуму та відсутності сайд-ефектів. | Не може делегуватися агенту. |
| **Documentation** | `type:docs`        | Оформлення технічної документації, архітектурних схем, опис ендпоінтів. | Виконується паралельно або після верифікації. |
| **Gate** | `type:gate`        | Контрольна точка дозволу або заборони переходу до наступного етапу (GO / REVISE / ABORT). Не виробляє код. | Блокує всі задачі наступного етапу. Human-only. |

### 4.1. Зіставлення первинної пропозиції кодингового агента та правок студента (Human Refinement):

1. **Спроба злиття тестів та коду**:
   - *Пропозиція агента*: агент спочатку згенерував спільні тікети «Implement & Test REQ-F-003», порушуючи послідовність TDD.
   - *Правка студента*: розділено на незалежні тікети `TICK-TEST-SUB-01` та `TICK-FEAT-SUB-01` із жорстким блокуванням: кодинг не починається, доки тест не створено і він не падає (Red-Green-Refactor).
2. **Спроба виходу за межі системи (Out-of-Scope violation)**:
   - *Пропозиція агента*: агент додав тікет «Feature: Integrate Stripe API for Paid Jam Submissions».
   - *Правка студента*: **Повне вилучення тікета**. У розділі 1.2.2 SRS v1.0 прямо зазначено, що грошові транзакції та платіжні шлюзи знаходяться Out-of-Scope.
3. **Виділення критичного валідатора SHA-256**:
   - *Пропозиція агента*: звичайна перевірка довжини рядка в інтерфейсі.
   - *Правка студента*: виділено окремий тікет безпеки `TICK-FEAT-HASH-01` з обов'язковою валідацією регулярного виразу `^[a-fA-F0-9]{64}$` на бекенді та захистом від ін'єкцій.
4. **Контрольні точки Stage-Gates**:
   - *Пропозиція агента*: трактування Gate як звичайного PR-рев'ю.
   - *Правка студента*: створено явні тікети `TICK-GATE-01` (PLAN-GATE), `TICK-GATE-02` (CORE-GATE), `TICK-GATE-03` (RELEASE-GATE), які блокують гілки та потребують підписаного протоколу перевірки.

## 6. Матриця розподілу відповідальності (Human vs Agent RACI)

| Тип задачі / Діяльність | Кодинговий агент | Людина (Студент / Lead) | Обґрунтування розподілу |
|---|---|---|---|
| **Формування та зміна меж системи** | Informed (I) | **Accountable (A) / Responsible (R)** | Визначення бізнес-цілей та бюджету є виключною прерогативою людини. |
| **Оформлення Addendum** | Consulted (C) | **Accountable (A) / Responsible (R)** | Будь-яка зміна SRS після baseline вимагає юридичного/авторського рішення. |
| **Розробка BDD/Unit тестів** | **Responsible (R)** | Accountable (A) | Агент швидко транслює формальні Given-When-Then у код тестів. Людина перевіряє коректність. |
| **Реалізація бізнес-коду (Feature)** | **Responsible (R)** | Accountable (A) | Агент реалізує код за строгими критеріями тестів під наглядом людини. |
| **Автоматизована верифікація (CI)** | **Responsible (R)** | Informed (I) | Рутинний запуск тестових раннерів та аналізаторів коду. |
| **Валідація задуму (UAT/UX)** | Not Involved | **Accountable (A) / Responsible (R)** | Тільки людина може оцінити реальну відповідність продукту потребам користувачів. |
| **Рішення Stage-Gate (GO/REVISE)** | Not Involved | **Accountable (A) / Responsible (R)** | **Human-Only**: юридична та технічна відповідальність за перехід між фазами проєкту. |
